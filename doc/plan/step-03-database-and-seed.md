# Шаг 3. Схема PostgreSQL, миграции и тестовые данные

**Статус:** завершён.

**Результат:** Prisma 7 подключена к NestJS через PostgreSQL adapter, создана первая миграция с доменными `CHECK`-ограничениями, ручной `db-tools` и идемпотентный seed.

## Цель

Создать устойчивую модель данных, обеспечивающую tenant-изоляцию и идемпотентный импорт.

## Что сделать

1. Подключить Prisma к `apps/api`.
2. Описать модели:
   - `Company`;
   - `Branch` с `companyId` и стабильным `externalId`;
   - `User` с ролью, `passwordHash` и nullable `companyId`;
   - `RefreshSession` с `tokenHash`, `familyId`, сроком действия и отметкой отзыва;
   - `DailyMetric` с филиалом, датой, счётчиками, числом новых отзывов, их средней оценкой, источником и внешним идентификатором;
   - `Review` с филиалом, рейтингом, текстом, статусом и датой публикации;
   - `ImportRun` с диапазоном, статусом `RUNNING`, `COMPLETED`, `COMPLETED_WITH_WARNINGS` или `FAILED`, количеством созданных/обновлённых/пропущенных записей и ошибкой.
3. Добавить ограничения:
   - уникальный email пользователя;
   - уникальный внешний идентификатор филиала;
   - уникальная пара `(branchId, date)` для дневных показателей;
   - уникальная пара `(source, externalId)` для импортированной записи;
   - рейтинг в диапазоне `1..5`;
   - неотрицательные счётчики;
   - `CLIENT` обязан иметь ровно одну компанию на уровне приложения; у компании может быть несколько клиентов;
   - дневной агрегат отзывов не вычисляется из таблицы `Review` и может охватывать недоступные системе тексты отзывов.
4. Добавить индексы по внешним ключам, `DailyMetric(branchId, date)` и полям активных refresh-сессий.
5. Создать первую миграцию.
6. Создать идемпотентный seed минимум для:
   - двух вымышленных компаний;
   - трёх филиалов;
   - администратора;
   - клиента одной компании;
   - дневных показателей за достаточный для графика период;
   - нескольких отзывов;
   - безопасных демонстрационных паролей.
7. Зафиксировать, что демонстрационные учётные данные допустимы только для локального окружения.

## Критерии готовности

- Чистая база создаётся миграциями без ручного SQL.
- Повторный seed не создаёт дубликаты.
- В базе есть данные, позволяющие проверить как агрегацию, так и изоляцию компаний.
- Все данные вымышлены.

## Зафиксированная реализация

- API переведён на ESM, Prisma Client генерируется в `apps/api/src/generated/prisma` и не хранится в Git.
- Для бизнес-сущностей используются UUID; даты аналитики хранятся как PostgreSQL `DATE`, технические даты — как `TIMESTAMPTZ(3)`.
- Удаление компаний и филиалов с зависимостями запрещено через `RESTRICT`; refresh-сессии удаляются вместе с пользователем; автор запуска импорта и ссылка на заменившую refresh-сессию получают `SET NULL`.
- База проверяет соответствие роли компании, нижний регистр email, диапазоны рейтингов, неотрицательные счётчики и корректность диапазона импорта.
- Миграции и seed не запускаются автоматически при старте приложения. Для них используется одноразовый сервис `db-tools`.
- Seed фиксирован и не использует Faker: 2 компании, 3 филиала, администратор, по одному клиенту каждой компании, 90 дневных агрегатов за `2026-10-01..2026-10-30`, 5 отзывов и один завершённый импорт.
- Все данные вымышлены. Локальные пользователи `admin@example.test`, `client.a@example.test`, `client.b@example.test` используют пароль `Demo123!ChangeMe`; эти доступы запрещено применять вне локального/demo-окружения.

## Ручные операции с БД

```bash
docker compose --profile dev run --rm db-tools pnpm --filter @tia/api exec prisma migrate dev --config prisma7.config.ts --name <migration-name>
docker compose --profile dev run --rm db-tools pnpm --filter @tia/api run db:migrate:deploy
docker compose --profile dev run --rm db-tools pnpm --filter @tia/api run db:seed
```

Команда `db push` и shortcut для `migrate reset` намеренно не добавлены: схема изменяется только версионируемыми миграциями, а удаление локальных данных должно быть явным действием.
