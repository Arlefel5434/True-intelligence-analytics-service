# Шаг 5. Роли и изоляция компаний

## Цель

Исключить доступ клиента к чужим данным не только в интерфейсе, но и через прямые API-запросы.

## Что сделать

1. Создать auth guard, который валидирует access JWT и формирует типизированного текущего пользователя.
2. Создать role guard/decorator для admin-only операций.
3. Ввести единый способ построения области доступа:
   - для `CLIENT` — только `user.companyId`;
   - для `ADMIN` — явно выбранная существующая компания.
4. Применять tenant-фильтр непосредственно в запросе Prisma, а не загружать запись без фильтра с последующей проверкой.
5. Для клиента не доверять `companyId` из query/body. Если параметр присутствует, сервер всё равно использует компанию пользователя либо отклоняет конфликтный запрос.
6. При запросе чужого филиала возвращать безопасный `404`, не раскрывающий факт существования ресурса.
7. Запретить клиенту:
   - просматривать список компаний;
   - запускать импорт;
   - получать филиалы другой компании;
   - запрашивать чужую аналитику по прямому ID.
8. Проверить защиту каждого endpoint при code review, а не только маршрутов аналитики.

## Критерии готовности

- Нельзя обойти tenant-изоляцию подменой query, path или body параметров.
- Клиент видит только свою компанию и её филиалы.
- Администратор может выбрать любую существующую компанию.
- Логика области доступа не размножена несогласованными копиями по контроллерам.
