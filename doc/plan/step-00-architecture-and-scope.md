# Шаг 0. Архитектура и границы MVP

**Статус:** завершён.

**Результат:** [архитектурный документ](../architecture.md).

## Цель

До написания кода зафиксировать состав системы, потоки данных и явно исключённую функциональность.

## Что сделать

1. Зафиксировать компоненты:
   - `web` — React SPA;
   - `api` — основной NestJS REST API;
   - `provider-mock` — отдельная имитация внешнего геосервиса;
   - `postgres` — основное хранилище.
2. Описать поток данных: `provider-mock → api → PostgreSQL → web`.
3. Зафиксировать область доступа:
   - `ADMIN` видит все компании, но работает в контексте выбранной компании;
   - `CLIENT` видит только назначенную ему компанию;
   - `companyId` клиента всегда определяется сервером из аутентифицированного пользователя.
4. Зафиксировать семантику дневных данных:
   - `views`, `websiteClicks`, `calls`, `routeRequests`, `newReviewCount` — значения за день;
   - `rating` — средняя оценка новых отзывов за день, а не накопительный рейтинг карточки;
   - период `from..to` включителен;
   - дата хранится как PostgreSQL `DATE`.
5. Зафиксировать границы первой версии:
   - без CRUD компаний, филиалов и пользователей;
   - без полноценного интерфейса отзывов;
   - без фонового планировщика импорта;
   - без ClickHouse, очереди и production-развёртывания.
6. Добавить краткую архитектурную схему в отдельный документ и ссылаться на `CONTEXT.md` как на словарь предметной области.

## Критерии готовности

- У каждого компонента есть одна понятная ответственность.
- Нет неоднозначности между просмотрами карточки и физическими посещениями филиала.
- Агрегация означает общий результат по всем доступным филиалам выбранной компании, а не смешивание разных компаний.
- Исключённая функциональность перечислена явно.
