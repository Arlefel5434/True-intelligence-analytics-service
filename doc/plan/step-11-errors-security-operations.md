# Шаг 11. Ошибки, безопасность и эксплуатационная готовность

## Цель

Сделать поведение системы предсказуемым при ошибках и закрыть основные риски тестового приложения.

## Что сделать

1. Ввести единый формат ошибок API с кодом, сообщением, HTTP status и correlation ID без stack trace для клиента.
2. Добавить глобальную валидацию DTO с удалением или отклонением неизвестных полей.
3. Добавить структурированные логи:
   - старт и результат импорта;
   - внешние ошибки без секретов;
   - ошибки авторизации без паролей и токенов;
   - correlation ID запроса.
4. Проверять `Origin` для изменяющих cookie-auth запросов и ограничить CORS известным frontend origin.
5. Настроить security headers, ограничение размера body и rate limit как минимум для login/refresh.
6. Не включать персональные данные, токены, пароли и API-ключи в логи.
7. Добавить readiness/liveness endpoints:
   - liveness не зависит от внешнего провайдера;
   - readiness проверяет обязательные зависимости приложения.
8. На frontend преобразовать технические ошибки в понятные сообщения и оставить возможность повторить безопасный запрос.
9. Проверить поведение при недоступности PostgreSQL и mock-провайдера.
10. Выполнить ручной security review всех tenant-запросов и cookie-настроек.

## Критерии готовности

- Ошибки API имеют единый безопасный формат.
- Секреты не появляются в ответах и логах.
- CSRF-риск cookie-аутентификации учтён проверкой origin и SameSite.
- Отказ внешнего источника не делает весь API неработоспособным.

## Зависимости

- Шаги 4–10.
