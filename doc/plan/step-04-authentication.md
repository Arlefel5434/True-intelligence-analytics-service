# Шаг 4. JWT-аутентификация и refresh-сессии

## Цель

Реализовать безопасный вход, восстановление access-токена и завершение сессии.

## Что сделать

1. Реализовать endpoints:
   - `POST /auth/login`;
   - `POST /auth/refresh`;
   - `POST /auth/logout`;
   - `GET /auth/me`.
2. Проверять пароль через `argon2` или `bcrypt`; никогда не возвращать `passwordHash`.
3. Выпускать:
   - access JWT примерно на 15 минут;
   - непрозрачный криптографически стойкий refresh token примерно на 7 дней.
4. Передавать токены через `httpOnly` cookies. В production использовать `Secure`; установить явные `SameSite`, `Path` и срок жизни.
5. Хранить в `RefreshSession` только хеш refresh-токена и идентификатор семейства токенов.
6. При refresh:
   - проверить сессию, срок и отзыв;
   - ротировать refresh token в транзакции;
   - сделать старое значение непригодным;
   - при повторном использовании старого токена отозвать его семейство.
7. Поддержать несколько независимых сессий пользователя.
8. При logout отзывать текущую сессию и очищать cookies.
9. Не сообщать при login, существует ли email: возвращать одинаковую ошибку для неверного email и пароля.
10. Ограничить CORS конкретным frontend origin и разрешить credentials.

## Критерии готовности

- После login `/auth/me` возвращает безопасный профиль.
- Истёкший access JWT восстанавливается через refresh.
- Refresh token ротируется и не хранится в открытом виде.
- Logout делает текущую refresh-сессию недействительной.
- Токены недоступны JavaScript-коду frontend.
