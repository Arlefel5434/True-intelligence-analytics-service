# Шаг 12. Автоматизированные тесты

## Цель

Проверить наиболее рискованные свойства системы: изоляцию данных, идемпотентность, аутентификацию и корректную агрегацию.

## Что сделать

1. Подготовить отдельную тестовую PostgreSQL или Testcontainers; тесты не должны использовать developer database.
2. Написать обязательный e2e-тест tenant-изоляции:
   - войти клиентом компании A;
   - успешно запросить свой филиал;
   - подставить ID филиала компании B;
   - получить безопасный отказ без утечки данных.
3. Написать интеграционный тест идемпотентности:
   - импортировать диапазон;
   - повторить импорт;
   - проверить отсутствие дополнительных `DailyMetric`;
   - проверить корректные счётчики результата.
4. Написать unit-тест агрегации:
   - сумма счётчиков;
   - средневзвешенный рейтинг;
   - поведение при нуле отзывов.
5. Написать тест refresh-ротации и запрета повторного использования старого токена.
6. Написать frontend-тест хотя бы одного сценария загрузки/ошибки и отображения пустого результата.
7. Добавить проверки ролей: клиент не запускает импорт, администратор может выбрать обе компании.
8. Сделать тесты детерминированными, независимо очищать данные и не полагаться на порядок выполнения.
9. Запускать lint, typecheck, unit/integration/e2e тесты отдельными командами и общей проверкой.

## Критерии готовности

- Выполнено требование минимум двух автоматизированных тестов.
- Tenant-изоляция доказана прямым API-запросом, а не только состоянием UI.
- Повторный импорт доказуемо не создаёт дубликаты.
- Тесты проходят повторно на чистом окружении.

## Зависимости
