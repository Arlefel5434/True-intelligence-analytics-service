# Архитектура аналитического кабинета

## Назначение

Система объединяет в одном кабинете аналитику карточек филиалов компании на геосервисах. Она показывает онлайн-взаимодействия с карточками — просмотры, переходы на сайт, звонки, построенные маршруты и новые отзывы, — но не измеряет физические посещения филиалов.

Основной сценарий клиента: выбрать период и один филиал либо все филиалы своей компании, затем посмотреть итоговые показатели и их динамику. Администратор сначала выбирает компанию и дополнительно может запускать импорт данных.

Предметные термины определены в [CONTEXT.md](../CONTEXT.md).

## Контекст и область данных

```text
Компания
├── Клиент 1
├── Клиент 2
└── Филиалы
    ├── Филиал A ── ежедневные показатели и доступные отзывы
    └── Филиал B ── ежедневные показатели и доступные отзывы
```

- Каждый `CLIENT` относится ровно к одной компании.
- У компании может быть несколько клиентов и филиалов.
- `ADMIN` не закреплён за компанией и выбирает одну компанию для просмотра.
- Аналитика разных компаний не смешивается.
- Режим «Все филиалы» агрегирует только филиалы выбранной или назначенной компании.

## Компоненты

| Компонент       | Ответственность                                                                                | Не отвечает за                                     |
| --------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `web`           | React SPA, вход, фильтры, карточки показателей, график, запуск импорта администратором         | Авторизацию данных и вычисление агрегатов          |
| `api`           | NestJS REST API, аутентификация, tenant-изоляция, импорт, агрегация, OpenAPI                   | Генерацию внешних данных и отображение UI          |
| `provider-mock` | Отдельный HTTP-сервис со стабильными вымышленными данными, пагинацией и тестовыми ошибками     | Доступ к основной базе и управление пользователями |
| `postgres`      | Пользователи, компании, филиалы, refresh-сессии, дневные показатели, отзывы и история импортов | Аналитический UI и вызовы внешнего источника       |
| `nginx`         | Production/demo: раздача собранного React, fallback для React Router и proxy `/api/*`          | Бизнес-логика и запуск frontend в development      |
| `db-tools`      | Ручной запуск Prisma migrations и seed в одноразовом контейнере                                | Автоматическое изменение схемы при старте API      |

`web`, `api` и `provider-mock` располагаются в одном `pnpm workspace`, но развёртываются как отдельные процессы и контейнеры.

Один `docker-compose.yml` содержит два взаимоисключающих profile:

- `demo` — immutable production-сборки API и mock-провайдера, Nginx со статическим React и PostgreSQL;
- `dev` — Vite и NestJS в watch-режиме с bind mount исходников, именованными dependency volumes и тем же PostgreSQL volume.

Оба режима публикуют только host-порт `8080`; остальные сервисы доступны исключительно во внутренней Docker-сети.

Миграции и seed выполняются явно через одноразовый `db-tools`; API не изменяет схему базы при старте. Prisma Client использует PostgreSQL driver adapter, а readiness API проверяет реальное соединение с базой.

## Границы сети

```text
Публичная граница

Браузер
   │ HTTPS / один origin
   ▼
Nginx (`web` production image)
   ├── /       → React SPA
   └── /api/*  → NestJS API

Внутренняя Docker-сеть

NestJS API ──HTTP + внутренний API key──▶ provider-mock
NestJS API ──SQL────────────────────────▶ PostgreSQL
```

- Браузер не обращается к `provider-mock` или PostgreSQL.
- `provider-mock` и PostgreSQL не публикуются наружу в production-конфигурации.
- Единый origin упрощает безопасную cookie-аутентификацию; API всё равно проверяет origin изменяющих запросов.
- В production/demo Nginx является единственной публичной точкой входа на `http://localhost:8080`: раздаёт статическую сборку React и проксирует `/api/*` в NestJS API.
- В development React запускается в Node-контейнере через Vite с hot reload на том же host-порту `8080`; Vite proxy сохраняет путь `/api`, поэтому отдельный Nginx в development не используется.

## Потоки данных

### Импорт

```text
ADMIN → web → POST /api/imports/statistics → api
api → provider-mock → страницы дневных данных
api → валидация и сопоставление филиалов
api → идемпотентный upsert → PostgreSQL
api → результат импорта → web
```

Импорт запускается вручную администратором и выполняется синхронно в рамках первой версии. Внешние записи имеют стабильные идентификаторы. Повторный импорт того же диапазона обновляет существующие данные и не создаёт дубликаты.

Неизвестный `externalBranchId` не создаёт филиал автоматически: запись пропускается с предупреждением. Некорректная запись отклоняет текущую страницу целиком; обработка следующих страниц продолжается.

Статусы запуска:

- `RUNNING` — обработка выполняется;
- `COMPLETED` — все страницы сохранены;
- `COMPLETED_WITH_WARNINGS` — часть страниц или записей пропущена;
- `FAILED` — ни одна страница не сохранена либо произошла системная ошибка до обработки.

### Чтение аналитики

```text
web → GET /api/analytics?from&to&branchId? → api
api → определение доступной компании из пользователя/выбора ADMIN
api → tenant-scoped SQL и агрегация → PostgreSQL
PostgreSQL → строки/агрегаты → api
api → DTO totals + series → web
```

Frontend никогда не читает PostgreSQL напрямую и не определяет область доступа. Даже прямой API-запрос клиента фильтруется по компании из его аутентифицированной сессии.

### Аутентификация

```text
web → /api/auth/login → api → PostgreSQL
api → httpOnly access/refresh cookies → браузер
web → защищённый запрос → api → tenant-scoped данные
```

Access JWT короткоживущий. Refresh token ротируется, хранится в базе только в виде хеша и может быть отозван. Подробная реализация относится к шагу 4.

## Семантика аналитики

Одна запись `DailyMetric` описывает один филиал и одну календарную дату.

| Поле              | Смысл за день                | Агрегация за период/филиалы           |
| ----------------- | ---------------------------- | ------------------------------------- |
| `views`           | Просмотры карточки           | Сумма                                 |
| `websiteClicks`   | Переходы на сайт             | Сумма                                 |
| `calls`           | Нажатия на действие звонка   | Сумма                                 |
| `routeBuilds`     | Построения маршрута          | Сумма                                 |
| `newReviewsCount` | Новые отзывы                 | Сумма                                 |
| `averageRating`   | Средняя оценка новых отзывов | Средневзвешенное по `newReviewsCount` |

Период `from..to` имеет включительные границы и задаётся календарными датами `YYYY-MM-DD`. Если новых отзывов нет, API возвращает `rating: null`, а UI показывает `—`, а не оценку `0`.

`Review` и `DailyMetric` имеют разные назначения. `DailyMetric` хранит авторитетный агрегат от источника. Таблица `Review` содержит только доступные системе отдельные отзывы; источник может не предоставлять тексты всех отзывов, поэтому количество строк `Review` не обязано совпадать с `newReviewCount`.

## Модель доступа

| Действие                                      | `CLIENT` |                          `ADMIN` |
| --------------------------------------------- | -------: | -------------------------------: |
| Войти и обновить сессию                       |       Да |                               Да |
| Видеть назначенную компанию                   |       Да |                               Да |
| Получить список всех компаний                 |      Нет |                               Да |
| Выбрать компанию                              |      Нет |                               Да |
| Смотреть филиалы и аналитику текущей компании |       Да |                               Да |
| Запустить импорт                              |      Нет |                               Да |
| Запросить чужой филиал прямым ID              |      Нет | Только после выбора его компании |

Для `CLIENT` сервер не доверяет `companyId` из URL, query или body. Область доступа всегда выводится из текущего пользователя и применяется непосредственно в запросе к базе. Чужой ресурс возвращается как `404`, чтобы не подтверждать его существование.

## Границы первой версии

В первую версию входят:

- две роли и серверная tenant-изоляция;
- выбор компании администратором;
- выбор одного или всех филиалов;
- фильтр периода, totals и временной ряд;
- отдельный mock-провайдер;
- ручной идемпотентный импорт;
- хранение доступных отзывов без отдельного модуля управления;
- миграции, seed, Docker Compose, OpenAPI и автоматизированные тесты.

Осознанно не входят:

- CRUD компаний, филиалов и пользователей;
- автоматическое создание неизвестных филиалов;
- перенос филиалов между компаниями и их архивирование;
- полноценный экран и обработка отзывов;
- фоновый планировщик и очередь импорта;
- несколько внешних источников;
- ClickHouse и поток сырых событий;
- production-развёртывание и production secrets management.

Филиалы первой версии создаются seed-данными и считаются статичными.

## Предполагаемое масштабирование

PostgreSQL достаточно для первой версии и нескольких тысяч филиалов с дневными агрегатами. При росте сначала добавляются индексы, partitioning, фоновые задачи, ограничение параллелизма, очередь и кэш. ClickHouse становится отдельным аналитическим хранилищем только при появлении большого потока сырых событий и тяжёлых многомерных запросов; PostgreSQL остаётся источником пользователей, прав и транзакционных данных.

- Детали JWT, refresh-ротации и cookies — шаг 4.
- Реализация tenant guards и scoped queries — шаг 5.
- Контракт mock API — шаг 6.

- DTO аналитики и OpenAPI — шаг 8.
- UI и состояния интерфейса — шаги 9–10.
