# Аналитика присутствия бизнеса на геосервисах

Учебный сервис для просмотра ежедневных показателей филиалов. Клиент видит только свою компанию, администратор выбирает компанию и запускает импорт из имитируемого внешнего API. Данные демонстрационные.

## Архитектура и стек

```text
Browser → nginx (demo) / Vite (dev) → NestJS API → PostgreSQL
                                             ↓
                                      mock provider
```

React, TypeScript, Tailwind и Recharts отвечают за кабинет и график. NestJS реализует аутентификацию, разграничение компаний, импорт и аналитику. Prisma и PostgreSQL хранят пользователей, филиалы, ежедневные показатели и историю импортов. Отдельный mock provider позволяет воспроизводить импорт без доступа к реальному геосервису. В demo-профиле nginx раздаёт собранный frontend и проксирует `/api`; в dev-профиле эту роль выполняет Vite.

## Требования и запуск

Нужны Docker Engine с Compose и свободный порт приложения. Node и pnpm на хосте не требуются. Скопируйте `.env.example` в `.env`. При занятом `8080` задайте согласованные значения, например `APP_PORT=8081` и `APP_ORIGIN=http://localhost:8081`.

```bash
docker compose --profile dev up -d --build
docker compose --profile dev exec api-dev pnpm --filter @tia/api run db:migrate:deploy
docker compose --profile dev exec api-dev pnpm --filter @tia/api run db:seed
```

Откройте `http://localhost:8080` (или порт из `.env`). API health: `/api/health/live` и `/api/health/ready`; Swagger: `/api/docs`. Первый запуск новой базы требует миграции и seed: статус healthy означает соединение с PostgreSQL, но не наличие таблиц. Seed повторяем, однако обновляет демонстрационные учётные данные и показатели; не запускайте его на собственных данных.

Для проверки собранного приложения используйте `docker compose --profile demo up -d --build`. На чистой базе примените миграции и seed через tools-контейнер:

```bash
docker compose --profile demo --profile tools run --rm db-tools pnpm --filter @tia/api run db:migrate:deploy
docker compose --profile demo --profile tools run --rm db-tools pnpm --filter @tia/api run db:seed
```

Затем перезапустите API, если он стартовал до миграции: `docker compose --profile demo restart api`. Dev и demo профили не запускайте одновременно на одном порту.

## Демонстрационные учётные записи

| Роль                       | Email                   | Пароль             |
| -------------------------- | ----------------------- | ------------------ |
| Администратор              | `admin@example.test`    | `Demo123!ChangeMe` |
| Клиент «Северная чашка»    | `client.a@example.test` | `Demo123!ChangeMe` |
| Клиент «Городская пекарня» | `client.b@example.test` | `Demo123!ChangeMe` |

Эти данные предназначены только для локальной демонстрации. Секреты из `.env.example` также не подходят для развёртывания вне локальной машины.

## Тесты

Тесты API используют отдельную базу `tia_test`, которую создаёт скрипт подготовки. Вне Compose задайте `ADMIN_DATABASE_URL` и `TEST_DATABASE_URL` для тестового PostgreSQL. Скрипт откажется готовить базу с именем, отличным от `tia_test`. В Compose эти переменные настроены у сервиса `db-tools`.

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm verify
```

В Docker dev-контейнере команды `lint`, `typecheck` и `test` запускаются через `docker compose --profile dev run --rm --no-deps workspace-init pnpm <команда>`. E2e запускаются отдельно: `docker compose --profile dev --profile tools run --rm --build db-tools pnpm --filter @tia/api run test:e2e`. Для общей команды `pnpm verify` нужен полный workspace и перечисленные выше переменные окружения. E2e выполняет миграции и seed именно в `tia_test`.

## Сценарий демонстрации

1. Войдите как `client.a@example.test`. Просмотрите «Все филиалы», выберите октябрь 2026 года, затем отдельный филиал. Карточки и график изменятся.
2. Запросите филиал другой компании напрямую. Например, после входа в браузере запрос к `/api/analytics?from=2026-10-01&to=2026-10-05&metric=views&branchId=30000000-0000-4000-8000-000000000003` вернёт `404` без чужой аналитики. Та же граница проверяется e2e-тестом.
3. Войдите администратором. Выберите компанию, откройте «Импорт данных» и запустите импорт за диапазон до 31 дня дважды. Второй запуск не увеличит количество ежедневных записей: неизменившиеся записи попадут в «Пропущено».
4. Проверьте переключение компании и филиала, ошибку пустого периода и состояния загрузки. Скриншоты для сдачи подготавливаются отдельно.

## Ошибки и безопасность

Ответы API при ошибке содержат `code`, `message`, `status`, `correlationId`; ошибки валидации также содержат `details`. Такой же ID передаётся заголовком `X-Correlation-Id`. Внутренний stack trace клиенту не возвращается. Логи фиксируют ID запроса, тип отказа и итог импорта без паролей, токенов и API-ключей. Cookie имеют `HttpOnly` и `SameSite=Lax`; изменяющие запросы проверяют Origin. CORS разрешает только `APP_ORIGIN`. Login и refresh ограничены по частоте. Liveness не зависит от PostgreSQL и provider; readiness проверяет PostgreSQL.

## Масштабирование и ограничения

При сотнях компаний сначала нужны поиск и пагинация списка компаний, индексы под фактические фильтры `(branch_id, date)` и контроль времени агрегирующих запросов. При тысячах филиалов импорт следует вынести в очередь и отдельный worker, выполнять порциями с ограничением параллелизма и rate limits внешнего API. Повторные задачи должны дедуплицироваться, а обработка оставаться идемпотентной. Для часто запрашиваемых итогов можно добавить Redis cache с инвалидированием после импорта, для чтения — реплики PostgreSQL, для больших таблиц — partitioning по дате. Метрики длительности импорта, ошибок provider и запросов к БД нужны для наблюдаемости.

ClickHouse оправдан при больших объёмах сырых событий и тяжёлых аналитических запросах; одно лишь число компаний не требует его. PostgreSQL остаётся источником транзакционных данных, пользователей и прав доступа.

Первая версия имеет ручной синхронный импорт, один mock источник, упрощённое управление пользователями, неполный модуль отзывов и дневную модель без сложных часовых поясов. Production secrets management и фоновые задачи пока отсутствуют.
